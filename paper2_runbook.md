## 1. What the study is

**The paper.** [`paper2.tex`](paper2.tex), "Applying Meta-Evaluation Benchmark Reviews to Requirement Decisions: An Executable Method", for REFSQ in Springer LNCS format.

**Terms** (use them the same way in the protocol, the paper, and here; the paper describes only the final design, with no earlier versions, drafts, or protocols):

| Term | Meaning |
|---|---|
| MESA | The rubric for reviewing AI benchmarks, from the MESA paper ([`mesa_paper.tex`](mesa_paper.tex)); Paper 2 cites `v5/rubric/rubric-v5.1.md` (`mesa-rubric-v5.1`; version 5 plus the outcome rule of feedback item 15) |
| Level | Claimed, Documented, Verified, Contradicted, Undocumented, or Not applicable |
| Rating form | The file recording one rating: level, check outcome, check kind, scope, detection limits, task defects, applicability, rated by and signed by (`audit_forms/`) |
| Coding agent | Gemini 3.8 Flash Medium in `agy` (`CONFIG_01_GEMINI_FLASH_MED`); GPT-6.1 Sol, medium effort, in Codex (`CONFIG_02_SOL_MED`) |
| Issue, task | A SymPy bug report later fixed with tests; a task is the issue text plus the code before the fix, with the fix's tests hidden |
| Session | One agent on one task, at most 15 minutes, no internet, no human input |
| Resolved | Every hidden test passes, within 15 minutes, with no rule broken |
| Resolve rate | The share of tasks resolved, with its 95% Wilson interval |
| Evidence status | Admissible, Inquiry Required, or Inadmissible |
| Decision | Accept, Reject, or Inconclusive from the resolve rate, made only when the evidence is Admissible; otherwise no decision, with every reason. "Verdict" is MESA's term for something else; do not use it for Paper 2's outputs |
| Source tasks | SWE-bench Verified SymPy tasks (issues 2016 to 2023): the benchmark evidence |
| Target tasks | SymPy issues whose fixes were merged 2026-06-13 to 2026-11-05, after both models' stated training cutoffs: the tasks of the direct test |
| Direct test | Each coding agent on the target tasks, from the repository the requirement is written for, decided by the same rule |
| Audit only | The tasks the executed checks show to be broken left out, with no criteria gate, as automated audits use their findings |
| ABC | The Agentic Benchmark Checklist (Zhu et al. 2025), the second review protocol; applied as its paper describes it: item scores, the decision on all source tasks, unmet items as caveats, no withholding |

Name models, never "the assistant": Claude Opus 5.5 (this Claude Code session) built the code and tooling and drafted the requirement; Claude Sonnet 5.5 subagents made the B07 cheating attempts, write the rating forms (runs A and B), and answer the ABC items. Say "resolve rate", not "pass rate".

**What Paper 2 does.** It asks whether benchmark results support a requirement on a coding agent. The method ([`paper2/method/evidence.py`](paper2/method/evidence.py)) follows MESA's rules: input integrity; the evidence status from the rating forms; then a decision from the resolve rate only when the evidence is Admissible. **M1** and **M2** are the resolve rate alone (the same here); **M3** applies MESA, leaving out tasks whose tests a form shows to be broken. The decision on the requirement also needs the signed transfer justification.

**The requirement** (signed in `protocol-5/requirement.json`): "Working alone on a bug report from the SymPy repository, the coding agent changes the code so that the tests the maintainers later wrote for that bug pass, for at least 70% of bug reports, within 15 minutes each." It states its task set, the agent, a 95% confidence level, and `n_min` = 9 (the smallest number of tasks at which Accept is possible at 0.70).

**Research questions** (set 2026-11-09; gaps and sources in `protocol.md`; they name no repository, dates, or models):
- **RQ1:** How does reviewing a benchmark with MESA or ABC, beyond an automated audit, change the decision on whether a coding agent meets a requirement?
- **RQ2:** Does a decision from a reviewed benchmark agree with a direct test of the same requirement?
- **Control, not a question:** invalid sessions by kind and the resolve rate by test result alone.
- What earlier work already shows, and why the questions are about decisions: `supporting/editorial/paper2-mesa-refsq-review-2026-11-09.md`.
- What implementing MESA showed about MESA went to [`mesa_paper_feedback_from_paper_2.md`](mesa_paper_feedback_from_paper_2.md); the MESA paper adopted it as rubric version 5 (`supporting/editorial/mesa-v5-revision-2026-11-09.md`).

**The experiment (protocol 5)** ([`protocol.md`](paper2/preparation/protocol-5/protocol.md)).
- **Repository:** SymPy. **Agents:** two, each started once per task from a fixed script (`sessions/NN/run.sh`) with no input after the prompt.
- **Budget:** at most 90 sessions: pilot 1 task × 2 (slots 1–2); source 20 × 2 (3–42); target 20 × 2 (43–82); reserve up to 8, only to replace a recorded infrastructure failure (83–90).
- **Decision rule:** threshold 0.70, 95% Wilson rule. With 20 tasks, Accept needs 19 or 20 resolved, Reject 9 or fewer.
- **Rating forms:** eight (B05, B07, B12, B14a, B28a, B28b for the release or task scope; B14b per agent), from Claude Sonnet 5.5 runs A and B; run A's are signed. **ABC record:** one, from a Claude Sonnet 5.5 run; signed.
- **Policies:** strict (all seven at Verified) and lenient (B05, B07 at Documented, B28a, B28b; ignores B12, B14a, B14b).
- **Broken tasks:** a task whose tests a form shows to be wrong is left out of M3, and the score is reported with and without it.
- **Replay:** a test of the implementation (provenance removed, identity changed).
- **Valid session:** invalid, and not resolved, when its tool calls touch study material, call a tool outside the agent's local set, run a network command, when it received a message after the prompt, or when its patch changes a test-running file (`bin/test`, `runtests.py`, `conftest.py`, `pytest.ini`, `setup.cfg`, `tox.ini`, SymPy's `pytest.py`).

**Outcomes known in advance (state them in the paper).** With the eight MESA rating forms, the ABC record, and `requirement.json` signed by the author on 2026-11-09 (`audit_forms/completed/`, with 34 field-level edits from run A's drafts recorded in `audit_checks/signing-changes.json`): strict policy is Inadmissible (B14a, B28a failed) with inquiry on B12 and B14b; lenient policy is Inadmissible (B28a failed); MESA withholds its decision (`No decision`, not comparable to an issued decision for RQ2), while its counterfactual pre-gate score decision (`M3_withheld`, equal to `audit_only`) uses 14 tasks (Accept 14 of 14, Reject 6 or fewer); ABA flags 13031 and 18199, so its decision uses 18 tasks (Accept 17 or more, Reject 8 or fewer); ABC decides on 20 tasks (Accept 19 or 20, Reject 9 or fewer) with 15 caveats.

## 2. Rules for any AI working here

- **Model sessions start only from `run.sh`, after the author's authorization of that phase.** At the author's request (2026-11-06) the assistant may launch the protocol 5 pilot sessions and the sandbox checks. Never retry a session, never type into one, never run a model outside the ledger. The tooling still refuses provider adapters (`study_controls.launch`), and `sessions.py` never calls a model.
- **Never fabricate.** Write no human judgment, observation, signature, or authorization. Forms are drafted by the assistant and signed by the author with `sign-form` (never type `signed_at` by hand). Authorizations are written by the author.
- **Records are written once.** They are created with `save_new`, which refuses to overwrite. To correct a record, move it to a `superseded/` folder with a reason file (`targets.supersede`) and write a new one. **Never delete records, attempts, or logs**, not even on request: on 2026-11-06 trial 1 records were deleted on request, and only part could be recovered (section 8, item 18).
- **Protocols are frozen.** After a freeze, changing `protocol.md`, `configurations.json`, the prompt, the policy, any file in `sessions.CODE_FILES`, the Codex configuration, or the shared `agy` settings blocks every session (`frozen_drift`). A change needs a new protocol version, decided by the author, with the earlier records kept. Nothing learned from a session's result may change the rules of the same protocol.
- **Keep third-party copies out of the repository.** It is public. Third-party pages and papers are kept in `~/paper2-sources/`; the repository keeps only addresses, hashes, and short quotes ([`literature/notes/paper2-sources.md`](literature/notes/paper2-sources.md)). Development conversations (Antigravity, Codex) stay outside the repository; record their path and hash.
- **Repository rules.** Follow `CLAUDE.md` and `AGENTS.md`:
  - simple prose, few hyphenated terms;
  - do not compile LaTeX (report layout and page length as unchecked);
  - preserve historical records (protocol 4 under `paper2/preparation/protocol-4/`, protocol 3 under `paper2/preparation/v3/`, protocol 2.1 under `paper2/history/`);
  - commit only when the author asks.
- **The manuscript states only what the records show.** It does not say that `gpt-6.1-sol` at medium effort was planned before the protocol 4 pilot.
- **Disclose model work.** Record which Claude model did what in the forms' `roles.assistant`, the protocol, and the paper; name the model, never "the assistant".
- **Subagents run on Claude Sonnet 5.5** (`model: "sonnet"`), at the author's request (2026-11-08).
- **Pacing (internal only; never in the paper or the protocol).** Before each session, check the remaining quota: `agy -p "/usage"` for Gemini, and `rate_limits` in the last Codex rollout (`.../logs/rollout-*.jsonl`, `payload.rate_limits`) for Sol. Start a session only if at least 20% of the 5-hour limit and 10% of the weekly limit remain; otherwise wait for the reset. Measured per session: Gemini about 2% of the 5-hour limit and under 1% of the week; Sol about 1% and under 0.5%. A session cut off by a quota limit after its first tool call would count as not resolved.

## 8. Problems already found (look out for these)

1. **Nonexistent dataset revision.** The release record names a SWE-bench Verified revision (`d120a1bc…`) that does not exist. The rows come from the real revision `78f471bf…`. Do not "fix" the old record; it is historical.
2. **Constructed earlier targets.** The 20 protocol 3 target candidates look constructed (issue numbers in steps of ten). They are excluded from every role.
3. **Wrong image platform.** Docker on arm64 pulled the wrong platform, and the first harness run failed. A missing report is a harness failure, never task evidence.
4. **Unverified claims in protocol 3 review records.** The protocol 3 records cite "arXiv:2408.06292" as a SWE-bench Verified paper and "2,294 audited tasks". These claims could not be verified; SWE-bench Verified is an OpenAI post (1,699 tasks annotated). Do not reuse protocol 3 review records as evidence.
5. **SymPy now tests through pytest.** Target images install pytest and hypothesis, and target rows use `pytest -rA` with the `parse_log_pytest` parser. Source rows keep SymPy's own runner and parser.
6. **Grader rule.** A test has passed only when its status is PASSED or XFAIL. Test lists must follow the same rule (`targets.test_lists`).
7. **Collection errors.** Pytest stops the whole run at a collection error unless it gets `--continue-on-collection-errors`. The target test command has the flag.
8. **Stop rule.** Target processing must count only candidates earlier in the order. `select` blocks on any undecided task before the selected ones.
9. **Codex user configuration and memories.** The user's Codex configuration has plugins and global instructions, and a Codex home keeps `memories_1.sqlite` and thread history. Each session gets a fresh Codex home with only the sign-in and the fixed configuration.
10. **Whole-disk reads.** Agents on the host can read the whole disk. Isolation is observed in the logs (`ORACLE_MARKERS`), not enforced, unless a sandbox check shows reads blocked. The session's own workspace path is removed before matching.
11. **Steps are counted, not limited.** The 900 second limit is enforced by `run.sh`; a session over it is not resolved. There is no step limit since 2026-11-07 (problem 61); steps are counted from the log and reported.
12. **Client-reported identity.** Model and effort come from the client's own log, not attested by the provider (result "held").
13. **Grading failure.** If grading produces no report, `close` keeps an attempt and the slot stays started. Run `close` again; it refuses if the workspace changed.
14. **Network outages.** DNS for `api.github.com` failed for hours on 2026-11-06 (section 3).
